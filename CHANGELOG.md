### Fixed
- Divergence: psptool -h description differs from upstream __main__.py:63 ('Display, extract, and manipulate AMD PSP firmware inside BIOS ROMs.'); upstream tests/unit/test_cli.py fails against the Rust CLI (#96)
- psptool-cli: `psptool sign` and `replace -p` / `-R -p` re-sign an encrypted HeaderFile: both pass the Zen+ IKEK to `sign_entry`, the key upstream's `get_decrypted_body` always unwraps with (`get_unwrapped_ikek`, `header_file.py:286-307`), instead of none, which failed every one of the 256 encrypted signed corpus HeaderFiles with `NotEncrypted`. `cmds/sign.rs` and `cmds/replace.rs` are now routed (#108)
- psptool-ops: `sign_entry` (the `sign` and `replace -p` paths) refreshes a stale sha256 content checksum before signing like upstream's `resign_only` (`cert_tree.py:103-110` → `update_sha256`, `header_file.py:119-121`): when the header's sha256 bit is set and the digest at `0xd0` no longer matches the decoded body (a KeyStoreFile: its key store) — e.g. after `replace -s` — the fresh digest is written and the new signature covers it. Previously the header kept the old digest. A matching digest and a sha384 checksum are left alone. psptool-core's `entry::CHECKSUM_OFFSET` is now public (#109)
- psptool-ops: for a ROM that does not start at file offset 0 — behind a capsule header (`0x800` on ASUS `.CAP` and the Milan KRPA-U16 images, `0x220` on HP, more on Lenovo `.iso`) or the upper ROM of a dual-ROM image — the `ls` ROM row shows upstream's `Addr` (where the ROM starts, `rom.get_address()`) and `Size` (the ROM window, `rom.buffer_size`: 16 MiB on Milan, not the `0x1000800`-byte file; `psptool.py:71-72`, `blob.py:65`, `:72-75`), and the `Secondary Directory` column / `ls -j` `secondaryAddresses` list ROM offsets like upstream's `entry.file_offset()` (`directory.py:156-161`, `entry.py:38-70`; Milan `$PSP` → `0x272000`, was `0x272800`). Directory and entry addresses and the roundtrip are unchanged; the ROM rows and secondary cells of the 54 corpus images, the 5 local Zen 4/5 images and both Milan images now match the reference (21 + 2 + 2 differed) (#113)
- psptool-ops: the `ls` `Size` column and `ls -j` `size` of a HeaderFile / KeyStoreFile show upstream's `file.buffer_size` (`psptool.py:172`, `:249`) — the buffer re-sized to the normalised header `rom_size` (`header_file.py:72-75`, `:104-105`) — instead of the directory-declared entry size, matching what raw `-X` writes since #101. The 16 grown and 144 shrunk corpus HeaderFiles now match the reference, as does the Milan KRPA-U16 ABL0 (`0x3a0`, was `0x864f0` / `0x8c370`, #115); `differential.rs` compares `size` strictly for every entry (#111)
- psptool-ops: the `ls` Generation cell of a directory without a generation (one only FET slots reach, and its L2 directories) reads `None` like upstream, which prints `str(directory.zen_generation)` (`psptool.py:84`, `fet.py:89`, `directory.py:124`), instead of staying empty. The cell text now equals the reference's for every directory of the corpus (#122)
- psptool-ops: `ls -v` leaves `size_signed` / `size_full` / `size_packed` / `load_addr` empty on a KeyStoreFile row like upstream, which fills them only for an exact `HeaderFile` (`type(file) is HeaderFile`, `psptool.py:183-191`); `ls -j -v` `sizes` keep the key store (`issubclass`, `psptool.py:260`). The 12 corpus key-store rows now match the reference (#121)
- psptool-core+ops: the `ls` Generation column threads Zen generations like upstream's `zen_generation`: an L2 `$PL2` / `$BL2` directory inherits its parent's generation (`directory.py:81-82`, #116), a directory several combo entries point at lists every generation and passes the additions on to its L2 directories (`directory.py:61-62`, `:243-249`, #117), and each generation reads upstream's `Zen 3 (PSP ID 0xbc0c0140)` (`unknown (PSP ID 0x..)` for an unknown id) instead of `Zen3`, one per line (`fet.py:117-123`, #57). `walk_directories` records the ids on the new `DirectoryRef::generations`; `DirectoryProvenance::Tertiary` no longer carries a `generation`. The cell now matches the reference for all 433 directories of the vendor corpus and five Zen 4/5 images, except that a directory without a generation stays empty where upstream prints `None`
- psptool-ops: the `ls -v` `MD5` cell (sparse 4-char and default 32-char) and the `ls -j -v` `md5` of a HeaderFile / KeyStoreFile hash what upstream's `HeaderFile.md5` hashes, its data region `self.body` = `[0x100, rom_size - signature_len)` of the HeaderFile buffer (`header_file.py:106`, `:312-315`), not the whole directory-declared entry. All 4147 corpus HeaderFiles now match the reference's `md5()[:4].upper()`; other entries are unchanged (#119)
- psptool-ops: `ls -v` `size_packed` and `ls -j -v` `sizes.packed` of a HeaderFile / KeyStoreFile whose header `rom_size` is 0 show upstream's normalised `rom_size` — the directory-declared entry size, grown to the 0x100 header (`header_file.py:72-73`, `:32-33`) — instead of `0x0`. The 147 corpus HeaderFiles this hit (Summit-Ridge `0x1` / `0x8` combo parts, AORUS X570 `0x2e`, …) now match the reference (#118)
- psptool-ops: `ls` File Info of a HeaderFile / KeyStoreFile no longer carries the bare `signed` and `sha256` / `sha384` tokens; like upstream's `ls_files` (`psptool.py:113-140`) it lists only the outcome tags (`verified(..)` / `veri-failed(..)` / `key_missing(..)`, `sha256_ok` / `sha256_inconsistent`, else `sha384_*`). Every HeaderFile row of the 54-image corpus now matches the reference `ls -v`. The `ls -j` `info` list shares the tokens and drops them too (#120)
- psptool-core+ops+cli: raw `-X` (single- and multi-file) writes upstream's `File.get_bytes()`: for a HeaderFile / KeyStoreFile, the buffer grown to the header and re-sized to its `rom_size` (`header_file.py:32-33`, `:72-75`, `:104-105`), not the directory-declared entry. The new `Entry::file_bytes(blob)` provides it, and `extract_raw` takes the image (`extract_raw(entry, blob)`). The `-T` identical-bytes check compares the same bytes (`__main__.py:52-56`). All 4034 corpus HeaderFile-class files now extract byte-identical to upstream; 16 were short (grown past their directory size) and 144 were long (shrunk inside it) (#101)
- psptool-ops: `sign_entry` (the `sign` and `replace -p` paths) signs and patches the HeaderFile buffer like upstream's `resign_only` (`cert_tree.py:101-117`): the entry grown to its header and to `rom_size` (`Entry::header_file_window` of the editor's image), with the signature at `rom_size - signature_len` (`header_file.py:88`), not the directory-sized entry. The 13 corpus HeaderFiles grown past their directory size (`body too small`) and the 3 zero-size KVM_IMAGE records (`truncated`) now re-sign, and the reference's `SignedEntity.verify_with_pubkey` accepts them (new live-reference test `psptool-cli/tests/sign_oracle.rs`) (#105)
- psptool-core: `cargo doc` builds without warnings — `AddressMode::bits` links `Self::from_bits`, and the public docs of `get_decompressed_body`, `zlib_decompress` and `walk_directories` name the private helpers `zlib_find_header`, `zlib_decompress_strict` and `tertiary_actual_offset` as code instead of linking them (#106)
- psptool-core: a HeaderFile / KeyStoreFile directory record declaring fewer than 0x100 bytes (incl. size 0) parses its header like upstream, which grows the buffer to the header first (`header_file.py:32-33`): `classify` reads the 0x100 header bytes at the record's offset in the image (the entry body stays the directory-declared window), and `Entry::header_file_window` grows to `max(body, 0x100, rom_size)` so `rom_size == 0` reads as 0x100. The zero-size KVM_IMAGE records of ASUS_Notebook_TUF_FX505DY-AS.309 and Lenovo A285 / A485 are now HeaderFiles: `ls` / `verify` report their signature verdicts and `-X -u` matches upstream byte-for-byte; the decode-verification tally and `verify` oracle need no #90 tolerance (#90)
- psptool-core+ops+cli: `-X -u` / `-X -c` treat a `KeyStoreFile` like upstream: multi-file extraction transforms only exact HeaderFiles (`type(file) is HeaderFile`) and writes key stores raw — the 12 corpus key-store files now match upstream byte-for-byte (were `header ++ store`) — and single-file `-u` of a compressed key store is `KeyStoreFile.get_signed_bytes()`, `header ++ key_store`, via the new `HeaderEntry::get_key_store_signed_bytes` (`BodyError::KeyStoreTruncated` added). Multi-file `-u -k` / `-c -k` now PEM-encode pubkeys as upstream does (#100)
- psptool-core+ops+cli: `-X -u` / `-X -c` read a HeaderFile's `rom_size` buffer like upstream (`header_file.py:72-75`), not the directory-sized entry: `Entry::header_file_window(blob)` is public and `extract_decompressed` / `extract_decrypted` take the image (`extract_decompressed(entry, blob)`, `extract_decrypted(entry, blob, ikek)`); the CLI's single- and multi-file `-u`/`-c` and the inflate warning use it. The 13 corpus HeaderFiles grown past their directory entry, which failed `body too small`, now match upstream byte-for-byte, as do all 4019 corpus `get_signed_bytes()` and 256 `to_decrypted_file_bytes()` (#99)
- psptool-ops+cli: `verify` checks signatures against upstream's certificate tree — the decode-verification ladder's `CertifyingKeys::from_blob` (every ROM, every `$KDB` key-store key, every key under an id) and its signature rung, KeyStoreFiles signing header + key store — instead of a PubkeyFile-only first-writer-wins map; it decrypts with the Zen+ IKEK like `ls` (`verify_chain_of_trust`/`verify_with_directories` take `Ikek`, was `Option<Ikek>`; core `CertifyingKeys::add_entry` is public). Corpus, every ROM: 3409 verified / 377 bad-signature / 251 unknown-key / 0 errors (was 2993 / 26 / 380 / 638), matching the reference at all 3927 signed-file addresses (#93)
- psptool-core+cli: `-X -u` decodes zlib exactly like upstream 241629b: `HeaderEntry::get_decompressed_body` is `zlib_decompress(output[:zlib_size])` (per-magic priority search, strict inflate, a magic-free slice returned unchanged) and `get_decrypted_decompressed_body` shares the decode-verification ladder's decode, so a corrupt or truncated stream yields the still-compressed body plus upstream's `ZLIB decompression failed` warning instead of an error or a partial inflate; `get_signed_bytes` slices like Python instead of rejecting a body shorter than `size_signed`. `BodyError::{ZlibMagicMissing, ZlibSizeOutOfRange, SignedRegionOutOfRange}` removed. 79 corpus `-X -u` extracts that errored now match upstream byte-for-byte (#91)
- psptool-py: memory leak across ROMs — no parse was ever freed: pyo3 0.25 `#[pyclass(dict)]` types were not GC types, so upstream's reference cycles through instance `__dict__`s and the `NestedBuffer` parent link were invisible to the cycle collector. pyo3 0.29.3 (dict traversal), `NestedBuffer.__traverse__`/`__clear__`, weakref support on the graph classes, and a native-bytes trigger that runs `gc.collect()` at construction (DEVIATIONS.md 21). Parse-and-drop loop over 216 corpus parses (Python 3.13): before +32-48 MB retained per ROM (psp-etl hit an allocation failure before ROM 250); after a 384 MB peak (upstream PSPTool 672 MB) (#98)
- psptool-py: Python subclasses of the parsed model classes (PSP-DB's ROM-less `FakeHeaderFile(HeaderFile)`) instantiate without ROM arguments, and the `HeaderFile` decode ladder (`decode_verification`, `decode_verified`, `plaintext_identity_ok`, ...) runs upstream's call structure over their overrides and attributes; psptool-core exposes `body::decrypt` / `body::zlib_decompress` (`utils.py` primitives) (#97)
- Version skew: differential oracle (psptool 3.4) != translation source (git HEAD ~3.6) — needs alignment decision (#61)
- psptool-core: #59 zlib-recovery overrun check uses whole-file blob_end, upstream uses the ROM window (multi-ROM divergence) (#72)
- psptool-ops: replace.rs rewrite_size_field .expect can panic when zlib-recovered original_len exceeds u32 (R-CODE-2) (#71)
- psptool-core: #51 tertiary walk discards block[20:24] Zen generation id (ls Generation column diverges) (#70)
- psptool-core: entry address-mode divergence on upper-half (>16MB) directories — SP5 EPYC (#52)
- psptool-core: follow tertiary (0x48/0x4A) L2 directory pointers — Zen 4 double-indirection (#51)
